# 需求澄清

把模糊想法收敛成可交接的需求文档。先检查仓库事实，再问最少的问题；通过 `writing-plans` 成功落盘后结束，实施由用户在新的会话中启动。

## 何时介入

满足任一条件时使用：用户目标模糊；存在多个会产生不同外部行为的方案；范围、非目标或成功标准缺失且无法从上下文推导；接口、数据、权限、兼容性存在未决语义。新功能或跨层流程本身不意味着需要再次确认。

需求已经明确时不重复提问；一旦用户指定或当前流程已进入本 Skill，仍只整理文档并交给 `writing-plans`，不得以需求明确或原请求包含实施为由跳转执行。尚未进入本 Skill 的机械小改或具体 Bug 按全局路由处理。项目存在显式状态机、规划插件或更具体的项目 Skill 时，复用其文档格式，不并行创建另一套需求工件。

## 澄清深度

- **快速确认**：只有一个关键歧义。检查上下文，问 1 个决定性问题，确认后直接整理摘要并交接落盘。
- **常规澄清**：需要稳定范围或跨层契约。逐步确认问题、用户、范围、非目标、约束和成功标准。
- **方案探索**：存在多个合理架构、交互或接口方向。提出 2～3 个真正不同的方案，说明收益、代价、风险和适用条件，并给出推荐。

发现隐藏复杂度时可以升级深度；新证据证明问题更简单时也可收敛，不要求单向增加仪式。

## 工作方式

1. **先看事实**：读取最近层级规则、相关文档、真实入口、附近实现和必要的 Git 状态。不要把本可从仓库获得的信息问给用户。
2. **先拆过大目标**：如果请求包含多个可独立交付的子系统，先给出拆分和依赖顺序，再聚焦第一个可交付范围。
3. **按决策提问**：通常每轮只问一个会影响后续的问题；多个彼此独立、可一次回答的事实最多合并 2～3 个。优先给有限选项，也允许开放回答。
4. **比较方案**：只在确有选择时给 2～3 个方案；推荐项放在最前，并说明为什么适合当前仓库和约束。坚持 YAGNI，不把未来设想混入当前范围。
5. **形成需求摘要**：按 `references/requirement-brief-template.md` 的适用部分总结，不为了完整填充无关章节。
6. **确认关键决策**：如果摘要包含新推断、公共行为、数据或安全决定，请用户确认；用户原始请求已经明确授权的事实不重复确认。
7. **落盘交接**：关键决策确认后，在当前任务中读取并使用 `writing-plans`，传入完整摘要、确认依据、剩余开放项、仓库位置和文档路径约定，并明确标记“来源为 brainstorming；只输出文档；实施需由用户在新会话启动”。无需另问是否保存，也不只建议用户稍后调用该技能。原请求中的实施意图只作为文档范围依据，不作为本次交接自动实施的授权。
8. **核对并结束**：确认文档已实际写入且保留关键决定，返回可定位的绝对路径，并提醒：“请在新的会话中使用 `subagent-driven-development`，依据该文档开始实施。”可附一条包含实际文档路径的可复制提示，然后结束当前流程。不得调用执行技能、委派实施或自动创建执行会话。

## 完成标准

至少明确：要解决的问题、范围、非目标、可观察成功标准和仍然开放的决定。按需补充用户/调用方、接口和错误语义、数据与权限、兼容性、依赖和验证方式。摘要不得包含相互冲突的范围、模糊占位符或无法验收的“更好、更快、更稳定”。

`brainstorming` 的完成不仅是对话中给出摘要；摘要必须已交给 `writing-plans` 成功落盘，返回可定位的文档路径，并给出新会话实施提醒。若环境或项目约束导致无法保存，明确说明原因，不把未落盘状态描述为完成，也不把拟定路径交接为可实施文档。

## 边界

本 Skill 及其 `writing-plans` 交接只交付文档，不实现代码、修改运行配置、执行数据库写入或创建 commit。即使原请求包含“规划并实施”，也在成功落盘后停止，不直接使用 `subagent-driven-development` 开始实施。用户明确要求不落盘时遵从该例外，只交付对话摘要并说明未保存，不声称已满足文档落盘条件。
