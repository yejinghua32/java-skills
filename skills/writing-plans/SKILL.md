# 规划文档编写

把已确认需求转成恰到好处的需求、关键设计和实施计划。文档服务于决策、交接和执行，不为展示流程而堆叠模板。

## 何时落盘

满足任一条件时创建持久化文档：收到 `brainstorming` 完成后的摘要交接；用户明确要求；项目约定要求；工作预计跨会话或多人协作；跨模块/跨前后端；公共 API、数据迁移、权限、并发、部署等高风险变化；计划需要作为后续执行依据。

非 `brainstorming` 交接且需求明确、已要求实施、无需持久化计划的任务，可以按全局路由使用 `subagent-driven-development`。来自 `brainstorming` 的任务必须先按下述文档交接边界处理，不能走直接执行入口。需求仍有会改变结果的歧义时先使用 `brainstorming`。项目已有专属工件格式或状态机时复用它，不创建平行文档体系。

## 接收需求摘要

收到 `brainstorming` 交接后，在同一任务中完成实际保存，不再询问是否落盘。保留问题、范围、非目标、成功标准、关键决定、确认依据、约束及开放项；记录来源为 brainstorming 和“本会话仅交付文档，实施由用户在新会话启动”的边界。不将合理推断写成用户已确认的事实，也不把原请求中的实施意图转成当前会话的自动执行授权。

用户仅要求需求讨论或研究时，保存最小需求摘要/研究结论即可，不强制添加技术实施计划。原请求包含实施或明确要求计划时，再按下述流程补充可执行任务。检查已有相关文档并更新对应内容，避免同一需求重复建档。缺少必要输入时只报告真实缺口，不重新询问已确认的选择。

## 文档规模

- **单一规划文档（默认）**：将需求、关键设计决定和实施任务写在一个文件中，适合大多数常规任务。
- **拆分文档**：只有需求需要独立评审、架构决定复杂、实施计划较长或项目规范要求时，才拆为 requirement/spec、design、implementation plan。
- **多计划**：请求包含可独立交付的子系统时，先写总体依赖和边界，再为每个子系统分别规划；每个计划都应产生可运行、可验证的结果。

默认路径使用项目既有约定；没有约定时使用 `docs/plans/YYYY-MM-DD-<topic>.md`。日期使用执行时的本地日期，文件名简短、稳定且不包含敏感信息。用户指定位置优先。

## 编写流程

1. **读取输入**：接收并保留已确认的需求摘要，读取相关文档、代码入口、构建配置、测试结构和必要 Git 状态。计划必须基于真实路径和已有模式，不凭技术栈常识猜文件、命令或版本。若来自 `brainstorming`，不要重复开启需求澄清；仅在发现会改变行为、安全、兼容或数据结果的新矛盾时返回澄清。
2. **锁定边界**：写清问题、目标、范围、非目标、成功标准和开放项。开放项会改变行为、安全、兼容或数据时停止计划并返回需求澄清。
3. **记录必要设计**：只记录会约束实现的事实与决定，包括组件/数据流、接口和错误、权限、迁移、兼容、依赖及主要替代方案。简单任务不强制架构章节。
4. **建立交付映射**：每条成功标准至少对应一个实施任务和一种验证证据；高风险拒绝/恢复路径也要有任务或检查。
5. **拆解任务**：按依赖排序为独立可验证增量。每项说明目标、精确文件或有界区域、接口/依赖、实施要点、完成条件和权威验证命令。不要把 setup、文档和测试机械拆成没有独立价值的任务。
6. **写入并自审**：保存后读回文档，检查确认摘要是否完整保留，以及覆盖、顺序、路径/接口一致性、占位符、越界工作、回滚/兼容和命令可执行性。未实际运行的命令标为待执行，不编造验证结果；修正后返回绝对路径。保存失败时如实说明，不能以展示文档内容代替成功落盘。

需要持久化文档时读取 `references/planning-document-template.md`，只采用适用章节。模板是质量检查表，不要求空章节。

## 计划质量标准

计划必须让不了解当前对话但熟悉工程实践的开发者能够开始工作。禁止保留未完成占位词，也不要使用“适当处理错误”、“补充测试”、“类似前一步”等无法执行的描述。无需粘贴大段最终代码；只有接口签名、数据形状、配置或算法片段能消除歧义时才给示例。

任务粒度以“能独立验证并有明确完成结果”为准，不强制 2～5 分钟微步骤、每步 TDD 或每任务 commit。是否新增测试和运行范围由 `risk-based-testing` 根据风险决定。

## 执行交接

**先判断来源。** 来自 `brainstorming` 的交接只交付文档：成功保存并读回后，返回绝对路径，提醒用户在新的会话中使用 `subagent-driven-development` 依据文档开始实施，然后停止。即使原请求包含实现、修复或“规划并实施”，也不得直接调用执行技能、委派实施或自动创建执行会话。保存失败时报告原因，不能把文档标为已交付。

独立于 `brainstorming` 的规划请求沿用原有授权：仅要求文档时保存后停止；明确要求“规划并实施”且关键需求已确认时，可以转 `subagent-driven-development`。若发现无法从已有需求决定的业务、安全、兼容或数据语义，仅对该缺口请求必要输入；技术实现细节自主决定。不要把“批准写计划”推导为实施、push、PR、部署或其他外部操作授权。
