# 明确任务自主执行

把已明确的需求交付为经过验证的结果和聚焦本地 commit。先建立目标和完整任务清单，再按依赖执行；实现细节自主决定，常规步骤不设置用户确认关卡。

## 进入条件

执行依据可以是已明确的用户请求、已确认需求摘要、实施计划、任务文档或需求设计包，并且用户已要求实施、继续或恢复。来自 `brainstorming` 的文档必须由用户在新的会话中要求实施后进入本 Skill；不得从其澄清会话或 `writing-plans` 落盘交接直接进入，即使原请求曾包含实施。其他已经明确授权的执行任务不重复询问是否开始。仅讨论、评估或写文档不构成实施授权。

没有书面计划也可以执行：从明确需求提取目标、成功标准和任务即可，不为进入本 Skill 补写计划。只有项目要求、跨会话交接或任务风险确需持久化依据时才使用 `writing-plans`。关键需求确有未决语义时使用 `brainstorming`，随后遵守其只交付文档和新会话实施边界，不在落盘后自动恢复实施；当前目录存在项目专属执行状态机或更具体执行 Skill 时沿用它，不维护第二套进度。

## 启动不变量

**先建一个总体目标，再建完整任务清单。** 所有进入本 Skill 的任务都必须在修改任何代码、配置或交付文档前完成这两步，不以任务大小或是否已有计划作为豁免。目标包含预期结果、范围和可验证成功标准；清单覆盖全部已知实施任务、必要验证、交付核对，以及通过 `git-handoff` 完成本地提交。不得只列当前一步就开始实现。

优先使用当前环境允许调用的原生目标和 todo/计划工具。目标工具若要求用户或系统/开发者明确请求目标，只在该前提满足时调用；技能本身不能扩大工具权限。不满足调用条件或工具不可用时，将总体目标写在同一会话任务清单或已有执行文档顶部，明确验收条件并继续执行，不为工具限制额外索取确认，也不声称已创建工具目标。todo 工具不可用时，以已有计划 checkbox 或会话任务列表作为唯一进度源。

每个 todo 至少有稳定标识、预期结果、依赖、完成条件和状态；验证后补充证据。按可独立验证的结果拆分，不把每条命令建成任务。开始前展示目标和清单后立即执行，无需等待回复。

复用同一任务已有的目标和清单，恢复执行时先核对证据再更新状态。已有不相关工具目标时保留它，不覆盖、不错误标为完成；当前任务使用会话或文档记录。目标管理整体结果，todos 管理逐项状态；不要复制出互相竞争的进度记录。除非用户明确指定 token 预算，否则不设置 `token_budget`。

## 执行前审查

1. 读取完整需求及适用的计划、设计和最近层级规则，确认实施范围和验收依据。
2. 检查仓库真实入口、路径、接口、依赖和权威验证命令；检查 Git 分支、工作区与暂存区，识别用户已有修改。只在判断计划是否过期需要时查看历史。
3. 建立或复用总体目标，再创建完整 todos，并将成功标准映射到任务和验证证据。已勾选事项缺乏有效证据时进行聚焦复核。
4. 识别依赖、遗漏、风险和提交条件；非 Git 目录可以完成已授权修改，但必须记录本地提交条件不满足，不擅自初始化仓库。

路径变化、命令过期或任务顺序不合理时，基于仓库证据修正执行依据并继续。不得因为计划与实现细节不同就重复请求确认；是否需要输入由下述自主决策边界决定。

## 自主决策边界

- **直接决定并执行**：范围内的代码组织、命名、实现方式、已有依赖复用、验证选择、任务排序、局部重构和可恢复失败处理；遵守已确认契约并记录重要取舍，不逐项请用户选择。
- **更新依据并继续**：为满足原验收必需的遗漏、失效路径/命令或技术假设，在不改变约定结果、数据和安全边界的前提下自行修正，先更新清单，再执行新增工作。若有持久化计划，同步对应部分，不重新启动整轮需求确认。
- **只暂停受影响部分**：缺少无法从上下文确定的关键业务语义，或下一步超出已有授权且必须由用户决定时，保留现场并请求最小必要输入，同时继续独立任务。不能把“自主执行”当作新增范围、破坏性操作、外部写入或绕过权限的授权。

不询问是否开始、是否继续、用哪个执行模式、是否运行必要检查或是否创建已授权的本地 commit。进度更新用于说明结果和证据，不作为等待用户回复的门槛。

## 数据库连接与 SQL 授权

用户使用本 Skill 执行任务时，自动授权连接已明确的目标数据库，并执行完成当前需求、排错或验证所必需的 SQL。满足以下边界后直接执行，不反复询问是否允许连接、查看表结构或运行每条 SQL；这也是本 Skill 中任务所需数据库外部操作的授权依据。

- **确定目标**：从用户指令、当前项目连接配置或已配置连接器确定环境、数据库及适用的 schema/租户范围，复用现有凭据和访问方式。只读取定位目标所需的配置；多个目标无法唯一确定或环境不明时，不猜测、不默认视为测试库，只请求缺失的目标信息并继续独立任务。
- **默认允许**：任务必需的连接、元数据/结构查询和有限数据查询；非生产目标中范围明确、可恢复的插入、更新及非破坏性结构变更。无数据库操作需要时不为了检查权限而主动连接。
- **单独授权**：生产写入、删除数据、DROP/TRUNCATE、重置数据库、不可逆迁移和权限变更不包含在上述默认授权中。执行前必须已有针对目标、操作及影响范围的明确授权；已取得该授权时不重复询问。按操作实际效果判断，存储过程、脚本或迁移工具不能绕过此边界。
- **执行前自查**：核对目标和语句影响，将必要 SQL 工作与验证纳入任务清单；优先复用项目数据库工具或迁移入口。写入前检查筛选条件、预期影响范围与恢复方式，按数据库实际能力使用事务或项目恢复机制，不把“支持事务”当成所有操作都可回滚的保证。
- **结果与失败**：查询仅取任务所需字段和行数；执行后核对影响行数及预期状态，记录脱敏证据。失败或超时后先确认是否已经生效，再决定回滚或重试，不能盲目重复写入；不得因连接失败擅自切换数据库、提升权限或关闭安全检查。
- **凭据与限制**：不在命令输出、日志、回复、计划或提交中暴露密码、完整连接串及敏感记录。该授权不覆盖无关数据导出、跨租户操作或平台/工具权限限制；实际被拒绝时如实报告，不绕过限制。

## 执行方式

默认由当前会话按依赖顺序执行。只有至少两个任务可独立理解、验收且写入不重叠时，才使用 `parallel-work`；不因为计划有多个任务就自动创建子代理、worktree 或分支。

对每个任务：

1. 自行核对该 todo 的目标、文件范围、依赖和完成条件。
2. 将当前 todo 标记为进行中；同一时刻只保持必要数量的进行中任务。
3. 使用 `lean-development` 做最小实现；出现 Bug 或失败原因未知时转 `lean-debugging`。
4. 按 `risk-based-testing` 选择并运行聚焦验证；有计划时沿用仍适用的检查，命令过期时使用仓库权威入口并记录原因。
5. 检查实际 diff、范围和接口影响，再决定是否进入依赖任务。
6. 只有完成条件和验证证据满足后，才更新唯一进度源中的 todo 状态；若计划有完成标记，保持一致，阻塞、失败和跳过不得记成完成。
7. 计划中的 commit 安排不代表已授权 push、PR、合并或部署；最终本地提交由 `git-handoff` 检查条件和范围。

需要执行长计划或恢复中断任务时读取 `references/execution-checklist.md`。

## 检查点与漂移

在公共接口、数据迁移、权限、跨模块集成或高风险任务完成后，先复核需求映射、调用方、失败路径和验证证据，再继续依赖任务。普通任务不强制每步独立审查；高风险、大范围或主代理无法可靠判断时可以增加一次聚焦只读审查。

执行中发现原范围内的遗漏，补入 todos 后继续；已有计划按需同步。新增能力、改变已确认契约或绕过失败检查不能作为技术细节自行决定。仅因内部实现调整不返回需求澄清，也不把编写计划当成扩大范围的许可。

## 失败恢复与真实阻塞

验证失败先定位根因，自主修复当前任务引入的问题后重跑受影响检查；已有基线失败或环境问题应准确区分，不能为了通过而放宽正确期望。缺少依赖时先检查仓库声明和已有恢复途径，不擅自引入新的依赖策略。

连续 2～3 次尝试未缩小问题时停止重复尝试，汇总证据并切换调查假设或继续独立任务；只有确实缺少必要输入、操作授权或外部条件时才报告阻塞。文件归属不清时暂停该文件的修改或提交，保护用户现场。

记录已完成内容、未完成任务、失败证据、被否定假设和最小下一步。单次失败、普通检查点或等待输入不等于总体目标完成、暂停或阻塞；目标工具状态必须满足工具自身的更新条件，不为结束当前回复伪造状态。

## 完成与本地提交

1. 逐条核对全部 todos、成功标准与实际 diff，确保没有遗漏任务或未解释的状态。
2. 运行风险相称的最终集成验证，并使用 `lean-delivery` 核对范围、证据、文档和剩余风险。
3. **必须使用 `git-handoff` 创建聚焦本地 commit。** 本地提交是整体完成条件的一部分，不因任务小或没有书面计划而省略，也不再次询问是否提交。只暂存当前任务的修改，由 Git Skill 检查验证有效性、diff 归属、敏感信息和提交信息；整体完成时提交一次即可，不强制每个子任务提交。
4. 确认 commit 成功、记录提交标识并核对提交后的状态，再把提交 todo 标为完成。只有全部适用成功标准、最终验证和必需提交均满足，才将总体目标标为完成；工具目标遵守其完成条件。
5. push、PR、合并、发布、部署和清理仍需各自明确授权。

用户明确要求不提交时按要求豁免提交，并在清单中记录；验证后确无实际修改时记录提交不适用，不创建空 commit。这两类情况按调整后的完成标准核对目标。

非 Git 仓库、关键验证未通过、提交失败或改动归属无法安全区分时，保留现场并报告未满足的提交条件；可以报告实现和验证已完成，但不能声称整体已提交完成，也不能把包含必需提交的目标标为完成。不擅自初始化仓库、修改 Git 身份、绕过 hook 或夹带用户改动。
