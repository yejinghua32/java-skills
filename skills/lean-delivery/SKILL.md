# 精简交付

交付只陈述已经发生且有证据支持的事实。它是最终一致性检查，不是重新扩大实现或重复运行全部命令的阶段。

## 完成前核对

1. **范围**：工作区状态和最终 diff 只包含当前主题；没有无关格式化、调试文件、构建产物、敏感信息或用户修改被覆盖。
2. **行为**：逐条对照最初的 1～3 个完成标准。每条必须指向实现位置或明确说明未完成，不能仅用“测试通过”替代需求核对。
3. **契约**：改动触及公共接口、数据、配置、权限、部署或用户流程时，确认实现、调用方、迁移/兼容、错误路径和必要文档保持一致；不适用时不强制列清单。
4. **验证**：复用 `risk-based-testing` 已选择且仍然有效的证据。只有验证后代码变化、关键证据缺失或仓库门槛要求时才补跑；记录精确命令和状态。
5. **可交付性**：区分通过、失败、跳过、无法运行和已有基线失败。关键门槛失败时不得声称可安全合并、发布或部署。
6. **Git**：满足完成与验证条件后，普通任务可以按 `git-handoff` 创建聚焦本地 commit；由 `subagent-driven-development` 执行或用户明确要求提交时，提交是必需完成项，核对真实 commit 标识或明确记录豁免/阻塞原因。push、PR、合并、发布、部署和清理仍需各自明确授权。

## 结论分级

- **完成**：完成标准满足，必要验证通过，没有未披露的关键风险。
- **完成但有限制**：核心结果已交付，但存在不阻断当前用途的环境限制、跳过检查或已知风险；准确说明影响。
- **未完成/阻塞**：关键行为、验证、决策或外部条件缺失。保留现场，说明已完成部分、阻塞证据和最小下一步。

不要为了给出“完成”结论而淡化失败，也不要把建议、推测、未执行命令或计划写成已完成事实。

## 回复格式

非平凡文件改动优先使用：

```markdown
## 完成内容
- 描述实际交付的可观察行为。

## 修改文件
- `绝对路径`：说明修改目的。

## 验证结果
- `命令或检查`：通过 / 失败 / 跳过 / 无法运行，并说明范围。

## 风险与后续事项
- 只列真实未解决事项；没有则写“无”。
```

机械小改可缩短为 2～4 条。内容较多时按影响分组，不罗列每个无意义的生成文件或重复日志。
