# 精简调试

先缩小问题，再修改代码。区分已观察事实、当前假设和尚未验证的信息；不要把相关性当根因。

## 最小流程

1. **固定现象**：记录触发输入、实际结果、期望结果、环境和最小复现命令。无法稳定复现时先收集日志、响应、调用链或失败测试，不凭猜测改代码。
2. **定位首个错误边界**：按实际系统检查 UI、网络、API、服务、数据、队列、外部依赖、构建和环境，只追踪与症状有关的数据流。阅读完整错误及最深相关 cause，而不是只看最后一行。
3. **建立一个假设**：写成“因为证据 Y，我认为 X 是根因；如果正确，检查 Z 会出现结果 W”。一次只验证一个变量，优先使用只读诊断、最小样例或现有测试。
4. **修复根因**：确认假设后做最小改动。不得通过吞异常、无限重试、扩大超时、放宽权限/校验、关闭检查或修改正确测试期望来制造绿色结果。
5. **证明修复**：先重新运行原始复现，再按 `risk-based-testing` 覆盖最可能受影响的相邻路径。验证后检查是否遗留调试日志、临时开关、测试数据或敏感信息。

## 跨层问题

当症状跨越多个组件时，先比较边界两侧的实际输入输出：请求、响应、序列化值、事务结果、SQL/消息或构建产物。只在疑似边界增加最少诊断信息，并在交付前删除或脱敏。外部服务和时序问题也要先证明失败模式，再决定重试、超时或降级策略。

## 回归测试

优先保留自动化回归，当 Bug 可稳定复现，或涉及业务规则、边界值、协议、权限、数据转换、并发与幂等。测试应观察外部行为并有独立预期；如果只能镜像实现或依赖大量脆弱 mock，说明替代验证和限制，不为数量制造低价值测试。

## 尝试纪律

每次失败尝试记录：假设、最小验证、结果和被否定内容。没有新证据时不得重复相似修复。连续 2～3 次尝试仍未缩小范围时停止编辑，汇总已知事实、已否定假设、剩余边界和下一项所需证据；不要继续叠加补丁。

## 完成标准

只有原症状消失、根因解释与证据一致、风险相称的相邻验证完成、最终 diff 仍聚焦且没有调试残留时，才能报告修复完成。明确区分代码缺陷、环境缺失、外部依赖失败和已有基线失败。
