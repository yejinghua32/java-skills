# 产品需求设计

先理解产品已经能做什么，再设计应该改变什么。输出以用户行为、产品规则和验收边界为中心，不以假设的技术方案替代产品决策。

## 适用范围

适用于用户提出产品功能设计、需求文档、PRD、页面/流程改造或新能力设计，并且当前项目事实会影响方案的任务。纯技术实施计划使用 `writing-plans`，已有计划的执行使用 `subagent-driven-development`，根因未知的异常使用 `lean-debugging`。

本 Skill 只调查和设计，不修改业务代码。用户同时要求“设计并实施”时，先完成并确认产品需求设计，再交给 `writing-plans` 生成实施依据；不要从产品设计直接跳到编码。

## 先了解已有功能

围绕用户目标做有界调查，不默认遍历整个仓库：

1. 读取最近层级规则、README、产品文档和已有需求文档。
2. 定位相关页面、路由、菜单、组件、接口、服务、数据模型、权限和测试；必要时运行只读查询或现有应用检查。
3. 还原当前用户、入口、主流程、状态变化、字段、成功结果，以及适用的空态、错误、拒绝和恢复路径。
4. 记录可以复用的能力、当前限制和证据路径。不能因为一次关键词搜索无结果就断言功能不存在。
5. 只把已观察事实写成“现状”；推断必须标明依据，无法从项目确认且会改变产品行为的问题再询问用户。

形成一个简短的现状基线：已有能力是什么、由谁使用、从哪里进入、关键流程和数据是什么、当前需求与现状的差距是什么。

## 判断扩展还是新增

文档必须给出明确结论，并说明依据：

- **扩展现有功能**：用户目标、主要入口、核心对象或生命周期与已有能力一致；新增行为能保持现有语义和兼容性；复用现有流程比建立独立概念更自然。
- **新增功能**：用户目标、角色、入口、对象生命周期、权限、数据归属或成功结果明显不同；强行扩展会让现有概念含义混乱、增加无关分支或破坏兼容性。
- **组合方案**：只有共享基础能力但产品入口或生命周期确实独立时使用。分别写清哪些部分扩展、哪些部分新增，不用“组合”回避决策。

判断时比较用户心智、信息架构、流程连续性、数据语义、权限边界、兼容影响和后续维护成本。不要仅因“改动文件少”选择扩展，也不要仅为架构整洁选择新增。

## 澄清产品决定

优先从项目事实回答问题。只有无法从仓库确认、且答案会改变用户行为、范围、数据、权限、兼容性或验收结果时才提问；通常每轮只问一个决定性问题，并给出基于现状的推荐选项。

关键决定未确认时可以保存调查结论和待决问题，但不得把草稿描述为最终产品需求。最终文档不得保留 TODO、互相冲突的规则或无法验收的“优化体验”“增强能力”等表述。

## 编写并落盘

读取 `references/product-requirement-template.md`，只使用适用章节。文档应保持示例所体现的简洁风格：先说明目标，再描述界面/流程、业务与数据规则、边界和验证，最后自检；复杂功能再补充角色、权限、状态或兼容性章节。

优先使用项目已有产品文档目录和命名约定；没有约定时保存到 `docs/requirements/YYYY-MM-DD-<topic>.md`，日期使用执行时本地日期。文件名应稳定、简短且不包含敏感信息。

文档至少包含：

- 当前已有功能与仓库证据；
- “扩展现有功能 / 新增功能 / 组合方案”的结论和理由；
- 产品目标、范围与非目标；
- 面向用户的入口、界面或交互流程；
- 可执行的业务规则、字段、状态或数据行为；
- 关键边界、失败/空态/权限/兼容场景；
- 可观察的验收方式；
- 自检结论和仍需决定的事项，没有则明确写“无”。

需求文档描述“产品应表现为什么”，不拆解代码任务，不虚构文件路径、接口签名、数据库结构或技术实现。只有当前产品约束确实要求时，才记录已有技术限制对产品方案的影响。

## 完成与交接

完成前确认文档与仓库现状一致，扩展/新增判断有证据，所有规则能够被观察或验证，并返回保存路径。用户只要求产品需求设计时到此停止。

用户明确要求继续实施时，在关键产品决定已确认后把该文档交给 `writing-plans`；后续实施授权、Git 操作和外部动作仍遵守各自边界。产品需求文档本身不代表已经授权编码、提交、push、PR 或部署。
